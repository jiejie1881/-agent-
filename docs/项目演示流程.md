# 物流车辆智能分配系统 Demo 演示流程

## 1. 项目简介

本项目是一个可运行的物流车辆智能分配系统 Demo / 内部测试版，覆盖基础资料、货物与温控能力、每日运营、自动派车、方案版本、人工调整、方案发布、Driver 配送执行、每日异常、JWT + RBAC、审计日志，以及带 RAG 和人工确认机制的 AI Agent。

系统的 Agent 分为三个阶段：Phase 1 使用只读 Tool 查询真实业务数据；Phase 2 将写操作转换为 Pending Action，只有具有权限的用户明确确认后才执行并记录审计；Phase 3 使用 RAG 检索企业规则文档。Agent 不绕过既有 Service、Repository、事务、RBAC 或 HITL。

当前版本适合面试、架构讲解和内部业务流程演示，不代表已经达到生产环境要求。

## 2. 技术栈

- 前端：Vue 3、Vite、TypeScript、Element Plus、Vue Router、Pinia、Axios
- 后端：Python 3.11+、FastAPI、SQLAlchemy 2.x、Pydantic 2.x
- 数据库：MySQL 8.4、Alembic（当前 18 个 migration，head 为 `20261001_18`）
- 地图：Leaflet、OpenStreetMap、OSRM 公共 Demo 路由服务
- 认证与权限：JWT Access Token、Refresh Token、RBAC
- Agent：OpenAI-compatible ModelClient、Tool Schema、Registry、Executor、Conversation、Pending Action / HITL
- 测试与部署：pytest、Docker Compose、Nginx

## 4. Demo 启动方式

推荐使用 Docker Compose，以 MySQL 作为真实数据库运行 Demo。

1. 确认 Docker Desktop 已由演示者手动启动。
2. 在项目根目录复制 `.env.example` 为 `.env`，配置数据库密码、`DATABASE_URL` 和 `JWT_SECRET_KEY`。不要提交 `.env`，也不要在演示中展示密钥。
3. 启动服务：

   ```powershell
   docker compose up --build -d
   ```

4. 查看状态：

   ```powershell
   docker compose ps
   ```

5. 首次环境如无用户，可通过交互式命令创建管理员，密码至少 8 位：

   ```powershell
   docker compose exec backend python -m app.scripts.create_user --username admin --role ADMIN
   ```

6. 幂等初始化完整 Demo 数据，并由真实自动派车 Service 生成当前 Demo 方案：

   ```powershell
   docker compose exec backend python -m app.scripts.seed_demo
   ```

   第二次执行不会重复创建用户、基础资料、需求或方案。脚本不提供清库或 reset 功能，也不会修改 `P2E2E_` 数据。可用 `DEMO_PASSWORD` 环境变量或 `--password` 为首次创建的 Demo 账号指定密码；已存在账号的密码不会被重置。

7. 访问地址：

   - 前端：`http://127.0.0.1/`
   - 后端健康检查：`http://127.0.0.1:8000/health`
   - OpenAPI：`http://127.0.0.1:8000/docs`

容器启动时由后端执行 Alembic migration；不能用 `Base.metadata.create_all()` 代替 migration。

### 每日异常工作台

入口为“派车中心 → 每日异常”（`/dispatch/exceptions`）。选择配送日期后，后端优先使用该日 `PUBLISHED` 方案；没有已发布方案时使用最新 `DRAFT`；都没有时仍返回空方案及可计划需求。也可手动选择指定历史方案，但取消方案仅供历史查看。页面将“方案内未分配”“方案外待计划”“方案车辆出勤/启用异常”和“已发布方案配送失败停靠点”分开统计；报告只读，不会重新派车或改变状态。时间来自日期字段的本地日期选择，不把日期转换为 UTC 时间戳。

面试演示时可以说明：高频、确定性的业务异常优先沉淀为普通 Service + API + Vue 工作台。这不依赖模型额度，输出稳定、响应和调用成本可控，也便于追溯；复杂的解释与交互分析再交给 Agent。当前环境若模型额度耗尽，工作台仍可直接演示，不伪造 Agent 回答。

2026-10-07 联调：用户手动启动 Docker Desktop 后，Backend、Frontend、MySQL 均为 `healthy`，真实 MySQL 的 Alembic 为 `20261001_18 (head)`。浏览器已检查无方案全零、最新草稿、已发布方案、方案外待计划、车辆异常和配送失败停靠点；这些结果也通过真实 API 查询交叉核对。每日异常工作台最终人工验收为 PASS：2026-10-03 自动选择 V3 `PUBLISHED`（方案 #14），未被 V1 `CANCELLED`（#3）或 V2 `DRAFT`（#4）污染；手动选择已取消方案时，页面明确标注仅供历史查询。通过浏览器离线模式模拟 API 失败后，页面未白屏、loading 结束、显示明确错误且不保留旧报告；恢复网络后报告重新正常加载。

## 8. Agent Phase 1 演示说明

Phase 1 是只读 Agent。完整调用链为：

```text
Vue → Agent API → AgentService → ModelClient → LLM Tool Call
→ Registry → Executor → 业务 Service → Repository → MySQL
→ Tool Result → LLM → Response
```

有模型额度时，使用以下固定问题：

```text
查询 2026-10-03 的配送需求。
查询 2026-10-03 的车辆出勤情况。
查询当天的派车方案。
这个方案有哪些未分配需求？
帮我检查这个派车方案有没有问题。
```

没有模型额度时，可展示已有真实会话：

- 会话 `#9`：查询 `2026-10-02` 的真实车辆出勤，验证单 Tool 调用。
- 会话 `#10`：同时查询该日期的配送需求和车辆出勤，验证多 Tool 调用。
- 会话列表和上下文可说明 Conversation 多轮持久化能力。

只读 Tool 查询真实业务数据库，但仍通过 Service / Repository，不直接绕过业务分层。

## 9. Agent Phase 2、Pending Action、HITL 与 Audit 演示

Phase 2 不允许模型直接修改数据库。模型提出写操作后，系统先创建 Pending Action，前端展示操作摘要、参数、风险和有效期；只有具备权限的用户点击确认，Executor 才调用既有业务 Service。取消、过期或执行失败都不会伪装成成功。

本次 Seed 预留的固定提问为：

```text
把配送需求 #18 从任务 #13 移动到任务 #11。请先生成待确认操作，不要直接执行。
```

预期链路为 `LLM → Pending Action → Vue Confirm`。确认前数据库不变化；确认后需求移动，Action 进入 `EXECUTED`，Audit Log 记录 `source=agent`、`tool_name`、`pending_action_id` 和执行用户。方案取消只适合放在演示最后，避免提前终止主业务故事。

| --- | --- | --- | --- | --- |
| `#1` | `#5` | 取消方案 `#1` | `CANCELLED` | 用户取消，未修改业务数据 |
| `#2` | `#5` | 取消方案 `#1` | `EXECUTED` | 已执行；Audit Log `#6` |
